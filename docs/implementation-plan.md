# NMNL-browser 実装計画

## 前提と環境

本計画は `docs/requirements-definition.md`(仕様の正)と `docs/decision-records.md` に基づく。

- 開発と検証は Devin VM(Linux)で行い、ネイティブビルドの実機検証も Devin VM の GUI で実施する。
- UI のモックは egui の WASM ビルドをブラウザプレビューで提示し、ユーザーの確認を得てから実装を進める(プロジェクトの UI モック先行ルール)。
- Windows 向けバイナリは GitHub Actions でクロスビルドし、実機確認はユーザー環境に委ねる。
- MiAuth の認可とタイムラインの実データ検証にはユーザーの misskey.io アカウントが必要で、認可ボタンの押下はユーザー作業となる。

## プロジェクト構成

単一クレートを想定し、構成と依存方向は次のとおりとする。
UI 層は API 層を直接呼ばず、イベント集約層を介する。

- `src/main.rs`: ウィンドウと tokio ランタイムを起動するエントリーポイント。
- `src/app/`: アプリ状態、カラム管理、イベント集約層への委譲。
- `src/ui/`: カラム、ノートカード、ピッカー、ビューア、設定画面の描画。
- `src/api/`: REST クライアント(reqwest)とエンドポイント単位の関数。
- `src/streaming/`: WebSocket(tokio-tungstenite)の接続管理、チャンネル多重購読、再接続。
- `src/model/`: ノート、通知、カラム構成などのデータ型。
- `src/mfm/`: MFM の部分パーサ(仕様決定 D の範囲)。
- `src/emoji/`: 絵文字の解決と一覧のキャッシュ。
- `src/media/`: 画像取得、メモリ LRU、ディスクキャッシュ。
- `src/config/`: 設定 TOML、トークン(keyring)。

中核ロジックの概要は次のとおり。

- カラムの状態機械: REST による初期取得、ストリーミングによる差分追加、`untilId` による過去方向のページング、カラムごとのフィルタ適用。
- 絵文字解決: ノートが返す絵文字マップを優先し、欠落分を個別取得してメモリ LRU とディスクにキャッシュする。
- ピッカー用絵文字一覧: 取得結果をディスクにキャッシュし、期限切れ判定で再取得する(容量と更新間隔は実装時に検証)。
- 接続管理: WebSocket 1 本に複数チャンネルを購読し、切断時は指数バックオフで再接続して欠落分を REST で補う。

## 実装時に検証する項目

要件定義書で「実装時に検証」と記した項目を、実装フェーズの冒頭で実在仕様に照合する。

- io フォークのエンドポイント名とパラメータ(タイムライン系、チャンネル系、絵文字系)
- ストリーミングのチャンネル名とメッセージ形式
- 通知一覧の API(グループ化の有無)
- 絵文字一覧の取得方法と容量
- MiAuth の要求権限とエンドポイントの対応

## フェーズ

各フェーズはおおむね 1 PR とし、進捗は本書のチェックリストで管理する。

- [x] Phase 1: プロジェクト骨格と CI
  - cargo プロジェクト初期化、eframe の空ウィンドウ、rustfmt と clippy、GitHub Actions(Linux と Windows のビルドと lint)。
  - 受け入れ条件: `cargo build` と `cargo clippy` が CI で通り、空のウィンドウが起動する。
- [x] Phase 2: 設定と認証
  - TOML 設定、keyring によるトークン保存(利用できない環境では永続化しない)、MiAuth 認可フロー(認可 URL 生成、ブラウザ起動、トークン取り込み、`i` による検証)。
  - 開発用にトークンを直接設定する入口を併設する(実装詳細)。
  - 受け入れ条件: 認可して取得したトークンで `i` が成功し、keyring 利用可能な環境では再起動後もトークンが復元される(利用できない環境では永続化されない)。
- [x] Phase 3: モデルと API 層
  - データ型、REST 実装(タイムライン系、`notes/show`、`notes/conversation`、`i`、`users/show`、チャンネル関連、絵文字関連)。
  - 受け入れ条件: 文書を根拠にしたテスト ID 付きの単体テストが通る。
- [x] Phase 4: ストリーミング層
  - 接続管理、多重購読、再接続。欠落補充は再接続契機の通知までで、REST での実データ補充は Phase 6 のカラム実装が担う。
  - 受け入れ条件: 購読イベントの受信と再接続のテストが通る。
- [x] Phase 5: UI モック(WASM)
  - デッキ骨格、カラムの追加/削除/並べ替え/幅変更、ノートカードの見た目(ダミーデータ)。
  - 受け入れ条件: ブラウザプレビューでユーザーが操作確認し、フィードバックを反映済み。
- [x] Phase 6: タイムライン系カラムの実接続
  - tl、notifications、mentions、channel の各カラム、ノート表示(MFM、絵文字、画像、CW、センシティブ)、会話ビュー、フィルタ、ページング。
  - 受け入れ条件: 実際の misskey.io で各カラムが更新され、要件 ID の検証表が通る。
- [x] Phase 7: 投稿と操作
  - 投稿フォーム(本文、CW、公開範囲、添付)、返信、リノート、引用、リアクションピッカー。
  - 受け入れ条件: 実アカウントで投稿と各操作が成功する。
- [x] Phase 8: 仕上げ
  - 画像ビューア、トレイ常駐、プロフィール表示、設定画面(キャッシュ消去など)、起動時間とメモリの計測。
  - 受け入れ条件: N-01 の目標値の計測結果を記録し、外れがあれば原因を報告する。
- [x] Phase 9: リリース整備
  - リリースワークフロー(Windows と Linux のバイナリ)、LICENSE とドキュメントの同梱、バージョン付与。
  - 受け入れ条件: GitHub Releases にバイナリが置かれる → v0.1.0 で Linux/Windows 両バイナリの公開を確認。

## 残課題・既知の制限

v0.1.0 リリース時点で把握している残課題。優先度は付けず、実機検証待ちと仕様上の制約に分けて管理する。

### 実機での再検証が必要な項目

| 項目 | 内容 |
|------|------|
| N-01 メモリ目標 | 検証 VM での実測 RSS は約 850MB(目標 150MB)だが、GPU 非搭載のため llvmpipe ソフトウェア描画(libLLVM JIT と GL ヒープ)が大半を占め、実機値を代表しない。実 GPU 環境で Release バイナリの再計測が必要。起動時間(146〜573ms、目標 2s)とバイナリサイズ(23.6MB、目標 30MB)は目標達成。 |
| F-09-4 トレイ常駐 | 検証 VM の Plasma パネルに StatusNotifier ホストがなく、トレイアイコンの登録・メニュー・クリック操作は未検証(TRAY-01)。最小化→非表示→外部経路での復帰自体は実装・確認済み。KDE/GNOME 等の実デスクトップで確認が必要。 |
| F-02-1 ≡ ドラッグ並べ替え | テスト環境の合成ドラッグでは掴めず、実マウスでの動作は未検証。設定パネルの「←左へ/右へ→」ボタン(別経路)は COL-21 で検証済み。 |

### 仕様上・環境由来の既知の制約

| 項目 | 内容 |
|------|------|
| Unicode 絵文字 | 同梱フォントは NotoSansJP サブセットのため、😀 等の Unicode 絵文字文字は豆腐表示の可能性がある(カスタム絵文字は画像表示で対応済み)。対応するかは別途検討。 |
| 動画・音声の再生 | 仕様決定 F どおり外部ブラウザへ委ねる仕様。アプリ内再生はしない。 |
| Cloudflare 429 | io 側のレート制限で頻出する場合があり、その間はタイムライン等の更新が遅れる。再試行(指数バックオフ)は実装済み(N-03)。 |
| トークン永続化 | F-01 どおり keyring のみ。keyring が使えない環境では起動ごとの認可または環境変数トークンが必要(永続化しないのは仕様)。 |
| 会話ビューの入れ子 | 深い返信チェーンの入れ子表現は簡易表示(表示規則は UI 層の責務とした判断)。 |

### 運用メモ(リリースワークフロー)

- actions/checkout@v4・actions/upload-artifact@v4 が Node.js 20 系のため非推奨警告が出る(現在は Node 24 で強制実行され動作中)。将来の Actions 更新時に追従する。
- ubuntu-latest は 2026-10 以降 Ubuntu 26 へ移行予定の告知あり。apt 依存名の変化に注意。

## 引き継ぎ手順

- 現在地は本書のチェックリストとマージ済み PR で確認する。
- ブランチは `devin/<unix 秒>-<短い件名>` とする。
- 実アカウントの認可を要する検証(MiAuth、実タイムライン表示、投稿)はユーザー作業となるため、当該フェーズの開始時に依頼する。
- 文書間参照は仕様決定の ID(例:「仕様決定 D」)で行う。
- テストは文書を根拠に ID を振り、結果を表で報告する。

## 検証方針

- 単体テストは API のモックレスポンスと MFM パーサを対象とし、テストケースにはテスト ID 帳簿の接頭辞と連番の ID を振る。
- UI は Phase 5 のモックでユーザーの確認を先に得てから実装を続行する。
- 実機検証は Devin VM の GUI(Linux)で行い、Windows 向けは CI ビルドの成果物をユーザー環境で確認する。
