# NMNL-browser 要件定義書

## 目的と背景

misskey.io の公式 Web UI が持つデッキ表示を、軽量に動作するデスクトップアプリとして再構成する。

公式クライアントはブラウザ上の大規模な SPA であり、多機能な代わりにメモリと CPU を多く使う。
本プロジェクトは、カラムに情報を並べて眺めるというデッキの体験に機能を絞り、Rust で書かれた単一バイナリのネイティブアプリとして提供することを目的とする。

名称は NMNL-browser(No Misskey No Life の略称)とする(仕様決定 H)。

対象インスタンスは misskey.io に固定する。
任意インスタンスへ接続できる汎用クライアントにしない判断により、インスタンス選択画面、サーバーごとの機能差の切り分け、未対応機能のフォールバックを設計から外せる。

## 対象環境の前提

本節の値は、執筆時点で misskey.io の `POST /api/meta` が返した確認値である。

- サーバーソフト: MisskeyIO/misskey(io フォーク)、バージョン `2025.4.1-io.12b`
- MiAuth: 有効(`features.miauth` が true)
- ローカルタイムライン、グローバルタイムライン: 有効
- 新規アカウント登録: 停止中
- ノート最大文字数: 3000

io フォークは本家 Misskey との API 互換を基本とするが、エンドポイント名やストリーミングのチャンネル名に差異が残る可能性がある。
本書で「実装時に検証」と記した項目は、実装フェーズで io フォークの実在仕様に照合して確定する。

## 用語

- **カラム**: デッキを構成する縦方向の一列で、タイムラインや通知など一つの情報源を表示する。
- **ノート**: Misskey における投稿で、リノート、引用、返信を含む。
- **MFM**: Misskey Flavored Markdown の略で、ノート本文のマークアップ言語。
- **カスタム絵文字**: インスタンスが登録する画像絵文字で、ノート本文とリアクションで使われる。
- **MiAuth**: Misskey のアプリ認証の仕組みで、ブラウザで認可してトークンをアプリへ引き渡す。
- **MVP**: 最初に実装して提供する最小構成。

## スコープ

### 対象とする機能(MVP)

- MiAuth によるログインとトークン管理
- カラムの追加、削除、並べ替え、幅の調整
- タイムラインカラム(ホーム、ローカル、ソーシャル、グローバルの切り替え)
- 通知カラム(種別フィルタ付き)
- メンションカラム
- チャンネルカラム(対象チャンネルを選択してタイムラインを表示)
- メインカラム(投稿フォームとノート詳細遷移の基点)
- ノートの表示(本文、画像、リノート、引用、返信、CW、センシティブ画像のぼかし)
- 投稿(本文、CW、公開範囲、画像添付、チャンネル宛て)
- 返信、リノート、引用、リアクション
- ストリーミングによるリアルタイム更新と再接続
- カラム構成と設定のローカル保存
- トレイへの最小化による常駐

MVP のカラム構成は仕様決定 C で確定した(main、tl、notifications、mentions、channel)。

### 対象外とする機能

明示しないと境界が曖昧になりやすいため、MVP で扱わない機能を列挙する。

- ウィジェットカラム、リストカラム、アンテナカラム、ロールタイムラインカラム(いずれも拡張候補)
- ダイレクトメッセージ、チャット
- 投票の操作とノートの編集、削除
- 動画と音声の内蔵再生(クリックで外部ブラウザを開く)
- リアクション数のライブ更新(ノート単位の購読)
- 複数アカウントの切り替え、他インスタンスへの接続
- ドライブ、アンテナ、リストの作成と管理
- デッキ構成のサーバー保存(公式クライアントのプロファイル連携)
- カラムの上下分割、背景画像のカスタマイズ
- AiScript、ページ、ギャラリー、Play などの拡張機能
- OS 通知(トースト)への新着転送(拡張候補)
- モデレーション操作
- ミュートとブロックの管理 UI(サーバー側の既存設定はそのまま効く)

スコープ外の機能も、UI 上で完全に不可視にはしない。
例えば投票付きノートは「投票(ブラウザで開く)」と表示してリンクを出す。

## 機能要件

ID は `F-01` 形式とし、テストケースとの対応は実装計画で定義する。

### F-01 認証

- F-01-1: MiAuth の認可 URL をシステムブラウザで開き、トークンを取得する。
- F-01-2: トークンは OS のキーリングに保存し、キーリングが利用できない環境では永続保存を行わず起動ごとの再認証とする。
- F-01-3: トークンが失効したときは再認証を促す。
- F-01-4: 要求権限は必要最小限とし、候補は read:account、write:notes、read:notifications、write:reactions、read:drive、write:drive、read:channels、read:user-groups とする(最終確定は実装時にエンドポイント仕様へ照合)。

### F-02 カラム管理

- F-02-1: カラムの追加、削除、ドラッグによる並べ替え、幅の変更に対応する。
- F-02-2: 各カラムは独立してスクロールし、独立して更新を一時停止できる。
- F-02-3: カラム構成(種類、順序、幅、カラムごとの設定)を保存し、起動時に復元する。
- F-02-4: カラムのヘッダーに種類名とカラム操作(設定、一時停止、削除)を置く。
- F-02-5: アプリは単一ウィンドウとし、カラム列の横スクロールで全体を辿れる。

### F-03 タイムライン

- F-03-1: タイムラインカラムはホーム、ローカル、ソーシャル、グローバルを切り替えられる。
- F-03-2: 初期表示は REST で取得し、以降の新着はストリーミングで差分追加する。
- F-03-3: 過去方向のページング(`untilId` によるカーソル)に対応する。
- F-03-4: 表示フィルタ(リノートを含む、返信を含む、ファイル付きのみ)をカラム単位で設定できる。
- F-03-5: ストリーミング接続は全カラムで 1 本に集約し、チャンネル単位で購読を多重化する。
- F-03-6: 切断時は指数バックオフで再接続し、復帰時に欠落分を REST で補う。
- F-03-7: チャンネルカラムは対象チャンネルを選択してタイムラインを表示する(チャンネルの選択方法は実装時に確定)。

### F-04 通知とメンション

- F-04-1: 通知カラムは通知一覧を表示し、種別(フォロー、リアクション、リノート、返信、引用、メンションなど)でフィルタできる。
- F-04-2: メンションカラムは自分宛のノートを表示する。
- F-04-3: 未読管理の有無と方法は実装時に確定する。

### F-05 ノート表示

- F-05-1: 本文は MFM の対応範囲として太字、斜体、取り消し線、コード、引用、リンク、メンション、ハッシュタグ、カスタム絵文字を描画し(仕様決定 D)、関数記法(`$[...]`)や HTML 系タグなど未対応の記法は除去したプレーン表示に落とす。
- F-05-2: カスタム絵文字は画像として表示し、ノートが返す絵文字マップを優先して欠落分をオンデマンドで取得する(取得方法は実装時に検証)。
- F-05-3: CW は折りたたみ、センシティブ指定の画像はぼかし表示を既定とし、クリックで展開する。
- F-05-4: リノート、引用、返信は深さ 1 段まで入れ子で表示し、それより深い参照はリンク表示とする。
- F-05-5: ノートを選択するとカラム内で会話ビュー(前後の会話)に遷移する。
- F-05-6: ユーザー名やアバターからユーザープロフィールを表示する(最低限は基本情報とそのユーザーのノート一覧とし、詳細な範囲は実装時に確定)。
- F-05-7: チャンネルへの投稿であるノートは、埋め込みのチャンネル情報に基づきどのチャンネルへの投稿かを表示する。
  - io 実測で `channel` オブジェクトに id/name/color が含まれる。
  - カード左端にチャンネル色のバーを描き、ノート下部(リアクション行の上)にアイコンつきのチャンネル名を置く(仕様決定 P)。
  - チャンネル名のクリックでそのチャンネルの channel カラムを開き、既存があれば差し替える(仕様決定 Q)。
  - 全カラムと会話ビューを対象とし、当該チャンネルの channel カラム内では省略する(仕様決定 R)。
- F-05-8: MFM の引用行は、行の内側のインライン装飾を残したうえで行全体を斜体にする(実装済みで、要件 ID の記載漏れを補記)。

### F-06 投稿

- F-06-1: 投稿フォームは本文、CW、公開範囲(パブリック、ホーム、フォロワー、ダイレクト)を入力できる。
- F-06-2: 画像添付はドライブへアップロードして付与する(枚数と形式の上限は実装時に確定)。
- F-06-3: 返信と引用は対象ノートへの参照を保持して投稿する。
- F-06-4: 投稿はチャンネルを宛先にでき、`channelId` を付けて `notes/create` で投稿する(実機フィードバック第 3 弾)。
  - チャンネルの選択 UI、公開範囲の扱い、対象ノートがチャンネル所属のときの返信、引用、リノートの扱いは協議中(U-11、U-12)。
- F-06-5: メインカラムから投稿できる(実機フィードバック第 3 弾)。
  - 投稿フォームの配置形態は協議中(U-13)。
  - 現状の常設ボトムパネルは F-06-1 の実装形態であり、配置の決定に従って見直す。

### F-07 リアクション

- F-07-1: ノートについたリアクションは絵文字画像つきで一覧表示する。
- F-07-2: リアクションはカスタム絵文字ピッカー(検索付き)で任意の絵文字を選択してつけられる(仕様決定 G)。
- F-07-3: ピッカー用にインスタンスの絵文字一覧を取得してキャッシュする(取得方法と容量の上限は実装時に検証)。
- F-07-4: カスタム絵文字リアクションのキー形式 `:name@host:` を解釈して表示する。
  - `@.` は投稿サーバー(本アプリでは misskey.io)の絵文字を指し、絵文字名でローカル絵文字として解決する。
  - `@<リモートホスト>` はノートの `reactionEmojis` マップ(io 実測でリモート分のみ収録される)の URL で表示する。
  - 解決できない場合は絵文字名のテキスト表示にフォールバックし、Unicode 絵文字は従来どおり文字で表示する。
  - 通知のリアクション欄も同じ解決で表示する。
  - リモートホスト絵文字バッジは、同名のローカル絵文字があれば `:name@.:` でトグルし、無ければ表示のみとする(仕様決定 O)。
- F-07-5: `notes/reactions/create` への送信形式はコロンを含む `:name:` または `:name@.:` とする。
  - io 実測: コロン無しの `name` や `name@.`、およびリモートホスト付きの `:name@<host>:` はいずれもサーバー側でハート絵文字へフォールバックする。

### F-08 メディア

- F-08-1: 画像はサムネイルをインライン表示し、クリックで拡大ビューアを開く。
- F-08-2: 画像は遅延読み込みとディスクキャッシュを行う。
- F-08-3: 動画と音声はインライン再生せず、クリックで外部ブラウザを開く(仕様決定 F)。
- F-08-4: センシティブ指定のメディアは既定で画像を描かず警告ラベルを表示し、クリックで展開する。
  - ビューアでも未開封のまま覆う(実装済みで、要件 ID の記載漏れを補記)。
- F-08-5: 添付画像はカラム幅に対して十分な大きさで表示し、原本が表示目標より小さい画像も拡大して表示する。
  - io 実測: `properties` に原寸が入り、`thumbnailUrl` は 500 ピクセル幅程度までで、原寸基準でしか拡大しないと小さい原本が判読しにくい大きさで残る。
  - レイアウトは添付枚数に応じたグリッドとし、1 枚は全幅で高さ上限つき、2 枚は横 2 分割、3 枚は左大 1 枚と右 2 枚、4 枚以上は 2 列とする(仕様決定 L)。
  - セルいっぱいまで拡大し、高さに上限を置く(上流公式の `object-fit: contain` 相当)(仕様決定 M)。
  - 高さ上限の目安は 360 ピクセル前後で実装時に調整する。
  - インライン表示には `thumbnailUrl` を優先し、未設定の画像は `url` にフォールバックする(仕様決定 N)。
  - 拡大ビューアは従来どおり `url` を使う。
- F-08-6: 拡大ビューアは Esc キーと戻る操作でも閉じられる(実機フィードバック第 3 弾)。
  - 戻る操作の範囲は協議中(U-08)。

### F-09 設定と保存

- F-09-1: 設定ファイルは OS の設定ディレクトリに置く。
- F-09-2: 保存対象はカラム構成、ウィンドウサイズ、カラムごとのフィルタ、文字サイズ(F-09-5)とする。
- F-09-3: キャッシュ(画像、絵文字)は容量上限つきの LRU とし、設定画面から消去できる。
- F-09-4: ウィンドウを最小化したときトレイに常駐し、トレイアイコンから復帰できる(仕様決定 K)。
- F-09-5: 文字サイズを設定画面から変更でき、設定を保存して起動時に復元する(実機フィードバック第 3 弾)。
  - 調整の方式と範囲は協議中(U-09、U-10)。

## 非機能要件

### N-01 軽量さの目標値(仕様決定 I)

- 起動時間: コールド起動 2 秒以内(計測条件は実装時に定義)
- アイドル時メモリ: 150 MB 以内を目安
- 配布物: 単一バイナリ 30 MB 以内を目安
- アイドル時 CPU: ストリーミング受信などのイベントがない限り定期的な再描画をしない

初回計測の結果は実装計画の進捗にあわせて記録する。

### N-02 セキュリティ

- トークンは平文ファイルに置かない(F-01-2)。
- 通信は HTTPS と WSS に限り、証明書検証を無効化する選択肢を持たない。
- 依存ライブラリはライセンスを確認してから導入する(プロジェクトの規約)。

### N-03 信頼性

- ストリーミング切断でタイムラインを失わない(F-03-6)。
- API のレート制限は指数バックオフで再試行する。
- 構成保存は原子的に書き換え、クラッシュでカラム構成を失わない。

### N-04 配布

- 対象プラットフォームは Windows と Linux とし、macOS は将来の拡張候補とする(仕様決定 B)。
- GitHub Releases からの単一バイナリ配布を基本とする。
- ライセンスは MIT とする(仕様決定 H)。
- UI の言語は日本語のみとする(仕様決定 J)。

### N-05 拡張性

- ホスト名は内部パラメータとし、API 基底 URL、ストリーミング URL、MiAuth URL をホストから生成する(UI への露出は misskey.io 固定)。
- インスタンス間の機能差は `meta` の機能フラグで吸収する設計とする。
- 複数アカウントや複数インスタンスの同時利用は対象外のままとする。

## 技術構成案

UI 基盤は仕様決定 A の egui(eframe)とし、構成要素は次のとおりである。

- UI は eframe と egui とし、即時モード GUI でカラムの自由配置と低いメモリ使用量を両立する。
- 非同期ランタイムは tokio とする。
- HTTP は reqwest、ストリーミングは tokio-tungstenite による WebSocket とする。
- API 層は自前の薄いクライアントとする(既存 crate の misskey-rs は Misskey 12.x 時代のもので io フォークの 2025.4.1 系に対応しない)。
- 絵文字と画像はオンデマンド取得、メモリ内 LRU、ディスクキャッシュとする。
- 設定は TOML とする。
- トークン保存は keyring クレートとし、利用できない環境では永続化しない。

通信の使い分けは次のとおり。

- REST は `i`、`notes/home-timeline`、`notes/local-timeline`、`notes/hybrid-timeline`(ソーシャル)、`notes/global-timeline`、`notes/mentions`、`i/notifications`、`notes/show`、`notes/conversation`、`notes/create`、`notes/reactions/create`、`notes/reactions/delete`、`drive/files/create`、`users/show`、`meta`、チャンネル関連(`channels/search`、`channels/followed` など)、絵文字関連(`emojis` の一覧と個別取得)の各エンドポイントを使う(名前はいずれも実装時に検証)。
- ストリーミングは `main`、`homeTimeline`、`localTimeline`、`socialTimeline`、`globalTimeline`、`channel` のチャンネルを購読する(チャンネル名は実装時に検証)。

構成は次の 3 層とする。

```
egui UI 層(カラムの描画と操作)
イベント集約層(1 本の WS の多重購読と REST 呼び出しの管理)
通信層(reqwest と tokio-tungstenite)→ misskey.io の /api と /streaming
```

## 検証とモックの方針

UI は、テストより先にユーザーの実機確認を要する(プロジェクトの規約)。
egui は WASM ターゲットを持つため、カラムレイアウトのモックを WASM ビルドしてブラウザプレビューで提示し、見た目と操作感を早期に確定する。
その後、ネイティブビルドでの実機検証に移る。

テストは文書を根拠に ID を振って管理し、結果を表で報告する(プロジェクトのテスト規約)。

## 協議中のフィードバック項目(実機フィードバック第 3 弾)

各項目は選択肢と推奨案を提示して協議中であり、確定後に仕様決定として `docs/decision-records.md` へ記録し、確定済みフィードバック項目の表へ移す。
本文の対応箇所は F-06-4、F-06-5、F-08-6、F-09-5。

- U-08 画像ビューアを閉じる操作(F-08-6)
  - Esc キーで閉じることは依頼どおり確定とする。
  - 「戻るボタン」の解釈が協議中: a) マウスの戻るボタンのみ、b) 画面上に「←」ボタンを置く、c) 両方(推奨案)。
  - 既存の × ボタンと ←→ キーによる画像送りは維持する。
- U-09 文字サイズの調整方式(F-09-5)
  - a) UI 全体を拡縮する(ボタンや画像も連動する、推奨案)、b) 文字だけを拡縮する。
- U-10 文字サイズの調整 UI と範囲(F-09-5)
  - a) スライダーによる連続値(推奨案、範囲 0.8〜1.5 倍で既定 1.0)、b) プリセット(小、標準、大の段階)。
- U-11 チャンネル投稿の選択 UI(F-06-4)
  - a) 投稿フォームにチャンネル選択を置く(フォロー中一覧と検索、既存のカラム用選択 UI と同じ構成)、b) channel カラムに「このチャンネルに投稿」の導線を置く、c) 両方(推奨案)。
- U-12 チャンネル投稿の公開範囲と対象ノートの継承(F-06-4)
  - 推奨案: 上流公式クライアントに倣い、チャンネル選択時は公開範囲をパブリックに固定してダイレクトを選べなくする。
    対象ノートがチャンネル所属のとき、返信、引用、リノートは `channelId` を継承して同じチャンネルへ投稿する。
    いずれも上流動作の推測に基づく候補であり、実装時に io の実在仕様で検証する。
- U-13 メインカラムの投稿フォーム形態(F-06-5)
  - a) メインカラムへ移設してボトムパネルを廃止、b) メインカラムへ移し、メインカラム未配置のときだけボトムパネルを自動表示(推奨案)、c) メインカラムとボトムパネルの両方に置く。
